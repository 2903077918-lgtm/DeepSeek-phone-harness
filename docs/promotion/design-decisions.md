# 给桌面 Agent 写手机遥控器：5 个我反复推翻的设计决策

> 功能可以慢慢加，架构决策必须在第一天想清楚。记录 DeepSeek Phone Harness 里 5 个被推翻又重来的设计决策，以及最终为什么这样定。

---

做 [DeepSeek Phone Harness](https://github.com/2903077918-lgtm/DeepSeek-phone-harness) 时，功能层面的坑（比如 ask_user_question 卡死）都写过了。这篇聊另一类更隐蔽的问题：**架构决策**。每一个都花了半天到两天论证，多数被推翻重来过。

## 决策 1：轮询，而不是 WebSocket/SSE 推送给手机

直觉：流式输出应该用 WebSocket 或 SSE 推给手机。我第一版也这么想——直到算了一笔账：

- Agent 端本来就要连一条 DSH 的 WebSocket（收事件）
- 手机端再开一条，就是**两头各一条长连接**，中间还要处理断线重连、心跳、消息序号
- 而宣传片要的是"4G 网络下手机也能看打字机"——**增量轮询每次只拉几百字节新内容**，网络抖动时自动重试，天然鲁棒

最终：**Agent 端一条 WebSocket 吃事件，手机端增量轮询拉缓冲**。手机 4G 下打字机效果流畅，还免费获得"断线恢复"。

## 决策 2：单文件前端，不引框架

前端最省事的方案是 React + Vite + 一堆依赖。但我给自己定了个硬约束：**手机打开一个 URL 就能用，部署就是复制**。

单文件 `relay.html` 意味着：没有构建步骤、没有路由、没有状态管理库——**手写状态对象 + DOM 操作**。代价是代码不像框架那么"声明式"，换来的是任何人 clone 下来就能跑，连 `npm install` 都不需要。

## 决策 3：RPC 全部走"信封"，不做类型体操

DSH 的 Web API 是 `{type:'client-request', rpcId, method, payload}` 信封。我一度想给每个方法写类型校验——后来发现这是浪费：

- 信封格式是**稳定协议**，参数是**易变业务**——把精力放在封装信封、统一错误处理
- 手机端只消费我归一化的 JSON，不直接碰 DSH 协议

结果：executor.js 里十几个方法全是"构造信封 + 解析 result"，20 行一个，全是复制粘贴——但**没人能改坏它**，因为逻辑不在里面。

## 决策 4：审批和提问共用一个 pending 表

DSH 的审批（`approval/requested`）和提问（`question/requested`）是两个通道。最初我建了两张表、两个 API、前端两套卡片渲染——维护成本翻倍。

后来意识到：**手机端它们都是"需要用户决策的卡"**。合并成一个 pending 表，`kind` 字段区分，前端一套卡片渲染逻辑分派。提问卡比审批卡多一个"回答协议"（`{answers:[{id,selected}]}`），仅此而已。

## 决策 5：任务队列串行，不做并发

手机可以同时发多个任务——要不要并发？试过，立刻放弃：

- DSH 会话是**单写**的，并发写会互相覆盖
- 并发意味着手机端要处理"哪个结果属于哪个任务"的配对

最终：**一个全局队列，同一时间只跑一个任务**，`/api/status` 返回 `pending` 计数，手机端显示排队数。简单、不会错、用户理解成本为零。

## 这些决策的共同点

回头看，5 个决策全是同一个原则：**把复杂度放在"确定不会错"的地方，把简单留给用户。**

- 轮询代替推送 → 复杂度在 Agent，鲁棒性给手机
- 单文件前端 → 复杂度在代码组织，零成本给部署
- 信封 RPC → 复杂度在协议层，稳定给业务
- 合并 pending → 复杂度在设计，简单给前端
- 串行队列 → 复杂度在等待，正确性给任务
