# 我踩过的 3 个坑：让手机控制电脑上的 Agent，没有想象中那么简单

> 表面上是一层 HTTP + 一个网页，实际上每一步都在跟"你以为"较劲。记录几个真实的坑，希望你能绕开。

---

做 DeepSeek Phone Harness 之前，我以为"手机远程控制电脑 Agent"就是个把网页搬到手机上而已。做完之后我承认：**想法 10 分钟，填坑一整周。**

记录 3 个真实的坑，每一个都让任务在线上"优雅地卡死"。

## 坑 1：Agent 一提问，任务就永久卡住

这是最阴的一个。

我们的中继服务监听 DSH 的审批通道（`approval/requested`），一切正常。直到某天测试任务**永远不结束**——不是报错，是挂着不动，`pending` 一直 +1。

查了两天才发现：DSH 的 Agent 会调用 `ask_user_question` 工具**反问用户**，而反问走的**不是审批通道**！它走的是另一条通道（`question/requested`）。我的中继只监听了审批，提问帧直接被我丢掉了。

结果：Agent 在电脑上等着人回答，手机这边毫无感知，任务永远挂起。**直到用户回答，它才会继续。**

修复：单独摄入提问帧，转发成手机上的"需要你回答"卡片，回答协议和官方 Web GUI 完全一致。

**教训：Agent 的实时事件流里，每一类帧都有它存在的意义，漏掉任何一类，任务就会以你想不到的方式卡死。**

## 坑 2：工具调用的结果，藏在两层嵌套里

手机端要展示"工具卡片"：工具名 + 操作路径 + 结果。名字好拿，路径好拿（从参数里提取），结果呢？

我以为 `tool/result` 事件的 content 就是 `[{type:'text', text:'...'}]`。天真了。真实结构是：

```json
content: [{
  "type": "tool-result",
  "content": [{ "type": "text", "text": "<path>...<content>..." }]
}]
```

**两层嵌套**，`toolCallId` 还在内层。第一版代码只取了一层，结果：工具卡片有名字有路径，结果永远是空的。

修复：递归收集文本 + 用 `source.callId` 配对调用和结果。

**教训：协议文档写得再清楚，也不如抓一次真实报文。**

## 坑 3：手机浏览器缓存，让用户永远看到旧界面

改完界面，手机打开——**还是旧的**。刷新、重启浏览器、换浏览器，都一样。

不是网络问题，是**缓存**：旧版界面被浏览器缓存了，`Cache-Control` 没设对。

修复：服务端给 HTML 加 `no-store, no-cache, must-revalidate`，从此每次打开都是最新版。

**教训：手机端 Web 应用，缓存策略和功能代码一样重要。**

## 为什么这些坑值得讲

因为每一个坑背后，都是"手机远程控制 Agent"这个场景的**真实复杂性**：

- 它不是一个静态页面，是一条**实时事件流**的忠实搬运工
- 它不是一个玩具，要处理**审批、提问、工具结果**这些生产级细节
- 它不是一个 Demo，要在 4G 网络下保持**低延迟、可重试、可恢复**

填完这些坑之后，现在的效果是：手机上的工具卡片长这样——

```
[📄 read]                          ● 完成
C:/Users/Joey/Documents/.../config.json
▾ 点击展开：完整参数 + 完整结果
```

Agent 每一步在做什么、动了哪个文件、结果如何，手机上看得一清二楚。Agent 要权限、要提问，手机弹卡解决，**任务永远不会因为"没人理它"而卡死**。
